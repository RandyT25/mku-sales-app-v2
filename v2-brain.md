## What this is

V2 of the MKU/MKS sales team PWA, built as a **completely separate project** from `RandyT25/mku-sales-app` (v1, live/production, used daily by ~14 field reps). V2 must never modify v1 or the `MKU-MKS-Area-Dashboard` pipeline repo — those are read-only references.

Live at: **`randyt25.github.io/mku-sales-app-v2`**

Full architecture reasoning and the original milestone spec live in the approved plan this repo was scaffolded from — see git history / ask for the plan doc if context is needed on *why* a decision was made, not just *what*.

## Architecture decisions (confirmed)

- **Backend: Supabase** (Postgres + Auth + Storage) for new write-heavy data — competitor price logs, customer contacts/visit notes, order drafts, canonical customer identity. Chosen over Firebase/Firestore because the milestone-1 features are relational/aggregate-query-shaped (filter by product × area, manager rollups), which Postgres fits naturally and NoSQL fights. Chosen over Cloudflare D1 because Supabase's built-in Auth/Storage/Studio (browser table editor) matter a lot for a solo maintainer who tests exclusively on his phone, not locally.
- **Auth: per-rep PIN.** Pick your name (like v1's dropdown), enter a short PIN. v1 had *zero* real authentication (just a name dropdown + `localStorage` remembering the last selection) — this is the first time the app has real identity, which write-heavy Supabase tables require for RLS.
- **Data visibility: team-wide.** Any rep can see any other rep's competitor logs and visit notes — maximizes intel-sharing value. Management sees everything via an `is_manager` flag on the `reps` table.
- **Offline: writes require a live connection, for now.** No local write-queue/sync in this first backend-backed milestone — revisit only if field connectivity proves to be a real recurring problem.
- **Read-only reference data is NOT duplicated into Postgres.** Targets, stock, SO/order history, and revenue-based customer data keep coming straight from the same Dashboard-repo feed v1 uses (`data_sales.js`, `customers.js`, daily FJ Excel files). Postgres only owns genuinely new data.
- **`products.js` / `toolkit.js` / `announcements.js` are forked once from v1**, not kept in ongoing sync — these are static files local to the v1 app repo (not part of the Dashboard feed), so v2 maintains its own copy independently going forward.

### Deliberate deviation from the original plan's file layout

The plan proposed splitting `sales.js`'s logic into one file per feature under `features/` (`target.js`, `pricelist.js`, `stock.js`, etc.) from the start. **I did not do that split yet.** Instead, `sales.js` (2264 lines) was ported **as a single file, `lib/app-core.js`, unchanged**, and `index.html`'s bootstrap script was updated to load it from its new path.

**Why:** manually re-splitting 2264 lines of interdependent global state and functions in one pass is exactly the kind of mechanical, hard-to-fully-verify transcription work that's easy to introduce a subtle bug in — dropping a function, missing a global reference, breaking an implicit ordering dependency — without a way to catch it except by exhaustively re-testing every screen. Since Phase 0's actual goal is proving the new repo/deploy/manifest setup works and matches v1 exactly, keeping the ported logic as one verified-identical file achieves that goal with far less risk than a big-bang refactor would.

**The plan going forward:** split `app-core.js` into `features/*.js` incrementally, **one module at a time, only when that feature is actually being touched** for a new Supabase-backed capability (e.g., when building the order-builder upgrade in Phase 5, extract just the order-builder logic into `features/order-builder.js` at that point, verify it still works, then move on). This spreads the refactor risk across many small, individually-verifiable steps instead of one large one, and means nothing gets refactored before there's a real reason to touch it.

## Phase 3: customer identity/dedupe — infrastructure DONE

Investigated first (via Explore agent) rather than assumed: today there are **three customer-identity surfaces that never cross-reference each other** — revenue history keyed by `(rep display name, opaque code)` from the external read-only Dashboard feed, delivery data keyed by free-text `nama_cust` string match, and the Order screen's customer field (free-text, zero validation). `mergeDuplicateCustomers()` (`lib/app-core.js`) already partially compensates for one dimension of this (same-rep duplicate `code`s sharing a name), but nothing reconciles across reps or against the free-text surfaces.

## Phase 5: order builder upgrade — DONE, verified live

Originally scoped as "reuse previous order, save drafts," but clarifying with Randy revealed the Order screen isn't an order-taking tool — customers send their own PO/WhatsApp with what they want; reps use this screen to build and send a **sales pitch/proposal** (new items to an existing customer, or an opening offer to a new one). Redesigned around that: a gap-analysis suggestion engine (what a customer *isn't* buying, not "recreate what they already buy") plus multiple named local drafts.

- `getPitchSuggestions()` (`lib/app-core.js`) — **real-data bug found and fixed during build**: the original design cross-referenced purchase-history `product.code` against `PRODUCTS.id` and used `product.category`, but production data has an entirely empty `category` field and `code` values are ERP/SO codes (e.g. `"PSJ0044"`) that never match the catalog's own ids (e.g. `"MKU001"`) — the same cross-system identity mismatch documented in Phase 3, showing up again at the product level. Replaced with fuzzy name-prefix matching (`_normProductName`/`_findCatalogMatch`, memoized) against the catalog — verified ~40-50% of purchased line items resolve to a real category across spot-checked customers, enough to reliably infer "categories this customer buys from" (not exact SKU-level novelty, which the data can't support).
- **Design simplified after Randy's review**: the first version had two suggestion buckets — "more from what they buy" and "new categories to try." Randy correctly flagged this as backwards: a customer who already buys a lot of Salmon doesn't need more Salmon suggestions (that relationship is already settled), and the bucket also had a real bug — it never excluded the exact already-bought items, so it could literally re-suggest a product the customer already buys heavily. Removed that bucket entirely; `getPitchSuggestions()` now returns only untapped categories.
- Order screen: `#order-cust` now autocompletes against `getRepCustomerList()` (already handles multi-area reps like Sriasih GT/MT). A recognized customer shows a "Suggested for [name]" panel — categories they've never bought from — one-tap add into the same cart `addToOrder()` already uses. Unrecognized name (new customer) → no panel, unchanged from before.
- Drafts: **local only** (`mkuv2_drafts_<repId>` in localStorage) — personal scratch work, not team-shared data, so no new Supabase table. Multiple named drafts (not just one resume-slot), save/list/load(with-replace-confirm)/delete, a "Drafts (n)" badge button next to the customer field.
- Verified end-to-end: suggestions render correctly against real customer data (no more re-suggesting already-bought items), add-to-cart works, save/load/delete drafts all work, per-rep localStorage namespacing confirmed, no regressions on other tabs.

## `010ebfc` — real root cause of "delete does nothing": native confirm() unreliable in installed PWA, plus FJ delivery 502s

Randy reported delete still doing nothing on Intel entries — this time on **both his own entries and teammates'**, which ruled out the RLS-permission read from the earlier round (deleting your own entry is already allowed by policy). Root cause: `deleteIntelLogConfirm()` and 5 other destructive-action call sites (`resetRepPin`, `loadDraft`, `deleteDraft`, `deleteContactConfirm`) all gated on native `window.confirm()` — `if (!confirm(...)) return;` with no error, no toast, no network request on cancel. Native `confirm()`/`alert()` are known to be unreliable inside installed/standalone PWAs on mobile (can silently return `false`, or never render), which is exactly how this app is used on Randy's phone — and exactly why it could never be reproduced in this session's desktop-Chrome testing.

Fix: added a custom in-app `confirmDialog(message, {danger, okLabel})` (`lib/app-core.js`, promise-based, `#confirm-overlay` markup in `index.html`, styled to match the existing bottom-sheet `.overlay`/`.prod-modal` convention) and replaced all 6 native `confirm()` call sites with it — removes the dependency on native dialogs entirely. Paired with a defensive honesty fix in `deleteLog()` (`features/competitor-intel.js`): uses `{ count: 'exact' }` and throws if 0 rows were affected, so a future RLS-blocked delete (e.g. a plain Manager without Super Admin trying to delete a teammate's entry — no policy grants that today) reports a real error instead of a false "Entry deleted" toast.

Same commit also fixed the `MKU%252031.xlsx` / `MKS%252031.xlsx` 502s: `index.html`'s `_loadFJDiv()` fallback and `_loadFJAll()`'s two `*_TODAY` fetches skipped the existing "does this file exist" `list.includes()` guard and unconditionally requested **today's** delivery file — confirmed via `gh api .../contents/uploads` that today's file genuinely doesn't exist yet (only tomorrow's is uploaded in advance). Added the same guard to those 3 call sites. Separately cleaned up a double-percent-encoding bug (filenames were built with a literal `'%20'` string, then re-encoded by `encodeURIComponent()`) to a single clean encoding layer — real space client-side, `FJ_FILE_RE` in `dashboard-proxy` updated to match a real space, explicit `encodeURIComponent()` server-side when building the GitHub Contents API URL.

## Food/Beverage/Nestlé % mismatch vs the official pipeline dashboard — investigated, not a bug
